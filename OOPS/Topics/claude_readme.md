**Amazon's Low-Level Design interviews for new grad positions have evolved from theoretical design pattern assessments to practical, Amazon-specific system implementations, with approximately 60-70% of interview loops now including an LLD component.** The three most frequently asked questions—Design Parking Lot, Design Pizza Ordering System, and Design Amazon Locker—appear consistently across all interview reports from 2023-2025. These interviews test not just your ability to write code, but your mastery of object-oriented principles, design patterns (especially Strategy and Factory), SOLID principles, and Amazon's Leadership Principles—particularly "Think Big," "Dive Deep," and "Insist on Highest Standards." The format typically allocates 45-60 minutes per round, with 20-25 minutes for the LLD problem and 20-25 minutes for behavioral questions, requiring candidates to write actual syntactically-correct code in proper OOP format rather than pseudocode.

The landscape has shifted significantly in 2024-2025, with Amazon introducing Amazon-specific systems (warehouse lockers, package management, bookstore word search) alongside classic problems, and the new interview loop structure now features distinct rounds: DSA-only coding, maintainable code with LLD focus, and pure Leadership Principles assessment. For new grads, distributed systems knowledge is explicitly not expected—the focus remains on class-level design, proper abstraction, and production-quality code that demonstrates extensibility and maintainability. Successful candidates consistently report that strong technical performance alone is insufficient; Amazon heavily weights Leadership Principles alignment, with multiple candidates noting rejections despite optimal solutions due to weak behavioral responses.

## Mastering the Design Parking Lot question

The Design Parking Lot question is Amazon's gold standard for evaluating Low-Level Design capabilities, appearing in approximately 80% of LLD preparation resources and consistently across interview reports from 2015 to 2025. Understanding this question deeply provides a template for approaching all other LLD questions.

### What Amazon actually asks

Amazon interviewers present this question with varying levels of detail. The basic version states: "Design an object-oriented parking lot. What classes and functions will it have?" More detailed versions specify: "The lot should indicate full and empty status, support Valet parking with spot finding, and include three parking types—regular, handicapped, and compact." Extended versions add multi-level support with multiple floors, payment system integration with ticket generation and hourly pricing, different vehicle types (motorcycles, cars, vans, trucks) with appropriate spot allocation, and advanced features like display boards, entry/exit panels, spot reservation, and electric vehicle charging stations.

Interviewers expect candidates to start with basic structure and progressively add complexity based on clarifying questions. The evaluation begins the moment you receive the question—candidates who jump immediately into coding without asking questions demonstrate poor requirements gathering skills. You must ask about vehicle types supported, parking lot size and capacity, single or multi-level structure, number of entry and exit points, payment system requirements and pricing models, spot allocation strategy (nearest entrance vs by type), display board needs, and special accommodations for handicapped or electric vehicles.

### The complete class structure

The core entities form a clear hierarchy. **Vehicles** require an abstract base class with attributes for licensePlate, vehicleType, and timeOfEntry, with concrete subclasses for Car, Truck, Van, Motorcycle, and Bus. Each vehicle type has different space requirements that influence spot allocation.

**ParkingSpot** requires similar abstraction, with an abstract base class containing spotId, spotNumber, floorNumber, isOccupied, vehicle reference, and vehicleType. Concrete implementations include CompactSpot for cars and motorcycles, LargeSpot for trucks and buses, MotorcycleSpot exclusively for motorcycles, HandicappedSpot with accessibility features, and ElectricSpot with charging capabilities. This hierarchy allows for polymorphic spot allocation where any spot subclass can be treated as a ParkingSpot.

**ParkingLot** should be implemented as a Singleton since only one parking lot instance exists in the system. It maintains name, address, parkingLotId, a list of ParkingFloor objects, lists of EntrancePanel and ExitPanel objects, a map of parking tickets keyed by ticket ID, and maxCapacity. Critical methods include parkVehicle accepting a vehicle and returning a ticket, removeVehicle accepting a ticket and handling checkout, hasSpace checking availability for vehicle types, isFull returning boolean, getCurrentVehicles returning count, getTotalSpots and getFreeSpots providing capacity information.

**ParkingFloor** represents each level with attributes for floorNumber, a list of ParkingSpot objects (often organized as a 2D array arranged in rows and columns for realistic modeling), and a DisplayBoard reference. Methods include addParkingSpot and removeParkingSpot for configuration, getAvailableSpots returning free spots, and getSpotsByType filtering by vehicle type.

**ParkingTicket** serves as the contract between customer and parking lot, containing ticketId or ticketNumber (unique identifier), vehicle reference, entryTime and exitTime timestamps, spotAssigned reference, and paidAmount. The critical calculateFee method computes charges based on duration and vehicle type, implementing the business logic for pricing.

**EntrancePanel and ExitPanel** handle customer interactions. EntrancePanel provides printTicket generating new tickets, scanVehicle identifying vehicle details (license plate recognition), and assignSpot implementing allocation strategy. ExitPanel implements scanTicket reading ticket information, processPayment handling payment flow, validateTicket checking ticket validity, and openGate controlling physical barrier.

**Payment classes** use the Strategy pattern with a PaymentStrategy interface and concrete implementations for CashPayment and CardPayment. A CentralPaymentSystem Singleton coordinates payment processing across all exit panels.

**ParkingDisplayBoard** shows real-time availability with attributes for floor reference and availableSpots by type, with displayStatus presenting information and updateStatus refreshing when spots change.

**Supporting classes** enhance the system: ParkingRate encapsulates hourly pricing models potentially varying by vehicle type or time of day; ParkingSpotManager implements the core allocation and deallocation logic, encapsulating different strategies; VehicleFactory creates vehicle instances based on type; ParkingSpotFactory creates spot instances; and FareCalculator computes fees based on vehicle type, duration, and applicable rates.

### Design patterns and SOLID principles in action

The parking lot question showcases multiple design patterns working together. **Singleton pattern** applies to ParkingLot and CentralPaymentSystem because only one instance should exist with global access. Interviewers expect you to explain when and why Singleton is appropriate, though over-reliance on this pattern is a red flag.

**Factory pattern** is essential for VehicleFactory and ParkingSpotFactory, encapsulating object creation logic and making it easy to add new vehicle or spot types. The factory method creates appropriate subclasses based on type parameters, demonstrating the Open/Closed principle where you extend functionality without modifying existing code.

**Strategy pattern** is perhaps most critical, allowing runtime algorithm selection for payment strategies (cash vs card), parking allocation strategies (nearest entrance, most free spots on floor, cheapest rate), and spot selection algorithms (smallest available that fits, reserve compact for compact vehicles). Each strategy implements a common interface, making them interchangeable and independently testable.

**Observer pattern** can enhance the system where DisplayBoard instances observe ParkingLot state changes, automatically updating when spots become available or occupied. This demonstrates loose coupling between display logic and parking logic.

**State pattern** is advanced but impressive, particularly for ParkingSpot states (Available, Occupied, Reserved, OutOfService) with clean state transitions and state-specific behaviors.

The SOLID principles manifest throughout the design. **Single Responsibility Principle** ensures each class has one clear purpose—ParkingSpot manages spot state, FareCalculator handles pricing, ParkingSpotManager coordinates allocation. **Open/Closed Principle** allows adding new vehicle types without modifying existing code through factory patterns and inheritance. **Liskov Substitution Principle** ensures any Vehicle subclass can replace Vehicle and any ParkingSpot subclass can replace ParkingSpot without breaking functionality. **Interface Segregation Principle** creates focused interfaces like PaymentStrategy rather than fat interfaces with unused methods. **Dependency Inversion Principle** makes high-level modules depend on abstractions (Vehicle interface, ParkingSpot interface) rather than concrete implementations.

### Scope management and common mistakes

The minimum viable design achievable in 15-20 minutes includes Vehicle and ParkingSpot class hierarchies, ParkingLot class with basic park and unpark methods, simple spot allocation logic, and clear relationships between classes. This demonstrates fundamental OOP understanding but typically earns only a borderline pass.

The standard expected design for 25-35 minutes adds multi-level support with ParkingFloor, ticket generation and tracking, different spot types for different vehicles, at least two design patterns (typically Factory and Strategy), entry and exit panels, and basic payment processing. This demonstrates solid LLD skills and earns a strong pass.

The advanced or excellent design achieved in 35-45 minutes includes payment system with Strategy pattern, display boards with real-time updates, parking rate calculations varying by hour and vehicle type, admin and attendant account management, thread safety considerations for concurrent access, multiple spot allocation strategies with clear trade-offs, and comprehensive edge case handling including lot full scenarios, invalid tickets, and payment failures.

Features typically out of scope unless explicitly requested include advance reservation systems, mobile app integration, database schema details, real-time navigation within the lot, license plate recognition systems, full valet service implementations, and electric vehicle charging management. Always confirm scope with your interviewer by asking directly: "Should I implement the complete payment flow, or focus on core parking logic?"

Critical mistakes include not asking clarifying questions before jumping into design, poor time management by spending too long on one component without completing core functionality, creating god classes where a single ParkingLot class handles everything including parking logic, payment processing, display updates, and user management, using primitive strings and integers instead of proper enums for vehicle types and spot types, not using or misusing design patterns (forcing inappropriate patterns or not explaining pattern choices), forgetting edge cases like lot full conditions, invalid vehicles, payment failures, and concurrent access scenarios, having poor code organization with no clear public vs private API boundaries, not showing scalability thinking by hard-coding floor counts and spot numbers, overcomplicating simple components with unnecessary abstraction layers, and for senior candidates not mentioning thread safety with multiple vehicles competing for the same spot.

Communication mistakes are equally damaging: not explaining reasoning for design decisions, being defensive when the interviewer suggests changes rather than adapting collaboratively, not thinking out loud during the design process, and saying "I don't know" without attempting to reason through the problem.

### What separates adequate from excellent answers

An adequate answer that earns a pass or borderline includes basic requirements coverage with Vehicle, ParkingSpot, and ParkingLot classes, working park and unpark functionality, correct inheritance usage, demonstrated OOP understanding, and reaching working code albeit with gaps. However, it uses limited design patterns (maybe one or two), may have design flaws, doesn't handle many edge cases, has limited scalability considerations, and provides basic rather than insightful explanations.

An excellent answer earning a strong hire demonstrates comprehensive requirements analysis through thoughtful clarifying questions, lists functional and non-functional requirements explicitly, discusses trade-offs between design alternatives, and shows depth of thought. The object-oriented design features clear class hierarchy with proper abstraction, well-defined responsibilities adhering to Single Responsibility Principle, multiple design patterns used appropriately (three to four), SOLID principles demonstrated in practice not just theory, and an extensible design where adding new features requires minimal existing code changes.

The complete solution fully implements or designs core functionality, selects appropriate data structures (HashMap for ticket lookups, Priority Queue for finding nearest spots), designs clean public APIs with proper public/private distinction, uses type safety with enums rather than magic strings, and demonstrates production-quality thinking. Advanced considerations include discussing concurrency and thread safety with locking strategies, handling edge cases gracefully with clear error messages, considering scalability both horizontal and vertical, implementing performance optimizations like O(1) ticket lookups and efficient spot finding, and mentioning database design if relevant.

Communication excellence manifests through thinking out loud effectively, explaining the "why" behind every decision, openness to feedback with quick adaptation when interviewers provide hints, using diagrams or notes to organize thoughts visually, and discussing alternatives with trade-off analysis ("Using X provides Y benefit but costs Z in terms of complexity"). Code quality includes clean readable formatting, proper naming conventions that are self-documenting, well-structured code not concentrated in single classes, and code that would be maintainable in production.

Amazon-specific success requires demonstrating Leadership Principles: **Think Big** by designing for scale beyond immediate needs, **Ownership** by taking responsibility for the entire system design including error cases, **Dive Deep** by showing technical depth when questioned about implementation details, and **Bias for Action** by making decisions efficiently without getting paralyzed by options.

### Time management in the 45-minute interview

The first 0-5 minutes should focus on requirements gathering with brief self-introduction (one minute maximum), asking clarifying questions (four minutes), and documenting requirements and assumptions. Your output should be a clear list of what you're building with interviewer agreement.

Minutes 5-15 cover high-level design: identify main classes and objects (three minutes), draw class diagrams or list relationships on shared screen (four minutes), discuss which design patterns to use and why (two minutes), and get interviewer buy-in on the approach. This phase produces a clear architecture plan that guides your implementation.

The implementation and detailed discussion from minutes 15-35 begins with core entities like Vehicle and ParkingSpot (five minutes), builds up to ParkingLot and manager classes (ten minutes), adds factories and strategies (five minutes), and discusses or implements key methods focusing on core park and unpark logic (five minutes). The key is balancing actual coding with discussion—you won't code everything but should implement critical parts demonstrating your coding ability while explaining other components verbally.

Minutes 35-40 cover edge cases and extensions: discuss edge cases like lot full and payment failures (two minutes), talk about scalability considerations (two minutes), mention testing approaches (one minute). This shows you're thinking beyond basic requirements to production concerns.

The final 40-45 minutes provide wrap-up: summarize your design hitting key points, ask the interviewer clarifying questions about their expectations or areas of concern, and clarify any unclear points. This professional close demonstrates communication skills.

Time management tactics include using a visible timer or clock, telling the interviewer your time plan upfront to set expectations, moving on if stuck rather than getting blocked, starting with the simplest working solution then iterating to add complexity, taking notes in a shared document for reference, and checking in with the interviewer at milestones to ensure alignment. Avoid spending more than ten minutes on any single class, trying to code every method perfectly with full implementation details, getting stuck on minor details like getter and setter implementations, coding silently for twenty minutes straight without explanation, and starting coding without design discussion.

If running behind at the thirty-minute mark and still on design, quickly outline remaining classes at a high level, focus implementation on two to three core classes only, discuss rather than code the rest, and prioritize the most important components: ParkingLot, Vehicle, ParkingSpot. If ahead of schedule at thirty minutes with core functionality complete, add the payment system demonstrating Strategy pattern, implement the display board showing Observer pattern, discuss concurrency considerations, add more design patterns where appropriate, and handle advanced edge cases.

## Amazon's LLD interview format and expectations

Amazon conducts LLD interviews in a standardized format optimized for evaluating both technical skills and cultural fit through Leadership Principles. Understanding this format allows you to prepare specifically for what interviewers evaluate and how time is allocated.

### Structure and evaluation process

Each interview round lasts 45-60 minutes, typically one hour, conducted virtually via Amazon Chime or similar platforms. The time allocation strictly divides into 20-25 minutes for LLD problem solving and coding, 20-25 minutes for Leadership Principles behavioral questions, and 5-10 minutes for candidate questions. This equal split between technical and behavioral underscores Amazon's culture-first hiring approach—technical excellence alone is insufficient without demonstrated Leadership Principles alignment.

The interview environment uses online code editors, typically Amazon's internal platform or shared documents, sometimes involving virtual whiteboarding. Candidates choose their preferred OOP language from Java, Python, C++, JavaScript, or Ruby. Critically, interviewers typically do not compile your code but review the structure, approach, and design thinking. This means syntactic perfection is less important than demonstrating proper OOP structure, but your code should be written as if it would compile.

The interview progresses through four distinct phases. **Problem clarification** in the first five to seven minutes assesses your ability to ask clarifying questions, understand requirements thoroughly, avoid making assumptions without verification, and identify functional versus non-functional requirements. Interviewers evaluate whether you exhibit customer obsession by understanding user needs and dive deep by asking probing questions about edge cases and constraints.

**Design and architecture** from minutes seven to twenty-two requires identifying key objects and classes, defining class relationships through inheritance, composition, and aggregation, sketching high-level architecture, and discussing applicable design patterns. Throughout this phase, thinking out loud demonstrates your problem-solving process—interviewers evaluate the journey as much as the destination.

**Implementation** from minutes twenty-two to forty-two focuses on writing modular, well-structured code following SOLID principles, using proper naming conventions for classes and methods, handling exceptions appropriately, writing code in proper OOD format with class definitions and object instantiation (not standalone functions), defining access modifiers clearly (public/private), and creating proper class structures with initialization methods. Amazon specifically expects "code in OOD format"—one candidate noted: "One thing common in all rounds was they wanted me to write the code in OOD format. It wasn't just writing the method and being done. They wanted object creation, function calls, etc."

**Follow-up and extension** in the final five to ten minutes tests adaptability with questions like: How would you extend this functionality to support a new feature? How could you optimize this design for better performance? What if we need to handle a new requirement that changes core assumptions? How would you test this system? What are the time and space complexities of key operations? Your responses reveal whether you designed for extensibility, considered trade-offs, and can think on your feet when requirements evolve.

### How LLD differs from System Design at Amazon

Low-Level Design for SDE I and new grad roles focuses on class-level design and implementation, object-oriented principles particularly SOLID, design patterns especially Strategy, Factory, Observer, Singleton, State, actual code implementation with syntactically correct classes and methods, data structures and algorithms within class methods, and thread safety and concurrency at the implementation level. The scope encompasses single applications or components with code-level details, specifically excluding distributed systems. Example questions include Parking lot, Elevator system, Library management, Hotel booking system, Chess game, and LRU cache.

High-Level Design typically for SDE II and above focuses on system architecture and components, microservices and API design, database design and schema selection, scalability and distributed systems patterns, load balancing, caching, CDN usage, CAP theorem and consistency models. The scope covers multiple services and components with infrastructure decisions like choosing between SQL and NoSQL, deciding on synchronous vs asynchronous communication, and selecting appropriate caching layers. Example questions include Design Netflix, Design URL shortener, Design Twitter feed, Design Amazon's recommendation system.

The key distinction is that LLD asks "How do you implement this feature with classes and code?" while HLD asks "How do you design a system that scales to millions of users?" For new grads, Amazon explicitly states that distributed systems knowledge is not expected for SDE I roles. You may encounter basic system design concepts, but the focus remains firmly on object-oriented implementation rather than distributed architecture.

### Leadership Principles in technical interviews

Amazon evaluates Leadership Principles even in technical rounds, with the most relevant principles for LLD being Dive Deep, Insist on Highest Standards, Ownership, Think Big, Invent and Simplify, and Learn and Be Curious.

**Dive Deep** manifests when you go into implementation details explaining time and space complexity, understand why you chose specific data structures, explain design decisions thoroughly with technical justification, and demonstrate depth of knowledge when questioned. In LLD interviews, this means not just stating "I'll use a HashMap" but explaining "I'll use a HashMap for O(1) ticket lookups because we need to validate tickets quickly at exit points with high throughput."

**Insist on Highest Standards** shows through writing clean, maintainable code with proper formatting, following best practices in OOP design, considering edge cases proactively, properly organizing code with clear structure, handling errors gracefully with appropriate exceptions, and thinking about testability from the beginning. Interviewers notice when candidates care about code quality rather than just functional correctness.

**Ownership** demonstrates when you take responsibility for the entire solution considering all components, think about how your design would be maintained and debugged, consider operational aspects like monitoring and logging, don't defer important decisions by saying "I'd ask someone else," and show you're thinking like an owner who will live with this code in production.

**Think Big** emerges when you design for scalability and extensibility beyond immediate requirements, avoid hard-coding values that limit future growth, create generic, reusable components that could serve multiple use cases, plan for future requirements even when not explicitly stated, and show you're not just solving today's problem but building a platform for tomorrow's needs.

**Invent and Simplify** appears when you find elegant solutions to complex problems, apply appropriate design patterns without over-engineering, avoid adding unnecessary complexity for theoretical future needs, explain trade-offs clearly showing you understand when simplicity trumps flexibility, and demonstrate that you can balance between under-designed systems that break easily and over-designed systems that are impossible to maintain.

**Learn and Be Curious** shows through demonstrating knowledge of design patterns and principles with examples, asking thoughtful questions about trade-offs and alternatives, being open to feedback and incorporating suggestions, discussing what you've learned from past projects, and showing genuine interest in finding the best solution rather than defending your first idea.

### What interviewers evaluate at every stage

Technical competencies form the core evaluation. **Code quality** encompasses readable, well-structured code with proper indentation and spacing, meaningful variable and function names that are self-documenting, modular design with clear separation of concerns, appropriate use of access modifiers marking public APIs and private implementation details, consistent style following language conventions, and helpful comments explaining complex logic without stating the obvious.

**OOP principles** evaluation focuses on encapsulation through proper use of private members with public interfaces, inheritance with proper class hierarchies that make logical sense, polymorphism using interfaces and abstract classes effectively, and abstraction hiding implementation details behind clear interfaces. Interviewers look for natural application of these concepts rather than forced usage just to demonstrate knowledge.

**SOLID principles** application is critical: Single Responsibility Principle with each class having one clear purpose and one reason to change, Open/Closed Principle where classes are open for extension through inheritance or composition but closed for modification, Liskov Substitution Principle ensuring derived classes can replace base classes without breaking functionality, Interface Segregation Principle creating specific interfaces rather than monolithic ones, and Dependency Inversion Principle depending on abstractions rather than concrete implementations.

**Design patterns knowledge** tests whether you know when and how to use Strategy Pattern for interchangeable algorithms, Factory Pattern for object creation abstraction, Observer Pattern for loose coupling between subjects and observers, Singleton Pattern sparingly for truly singular resources, Builder Pattern for complex object construction, Decorator Pattern for adding responsibilities dynamically, State Pattern for state-dependent behavior, and Template Method Pattern for algorithm skeletons with customizable steps.

**Extensibility and scalability** evaluation asks: Can your design accommodate new features without major refactoring? Is your code flexible for requirement changes? Did you avoid hard-coding values that should be configurable? Can new behavior be added through extension rather than modification? Did you design interfaces that won't break when implementation changes?

**Error handling** examines proper exception handling with specific exception types, edge case consideration including null checks, boundary conditions, and invalid inputs, validation logic at appropriate layers, graceful degradation when possible, and clear error messages that would help debugging.

**Data structure selection** evaluates appropriate choices for requirements, understanding of time and space tradeoffs when selecting between ArrayList vs LinkedList, HashMap vs TreeMap, understanding when to use Set vs List, and being able to justify data structure choices with complexity analysis.

**Communication** assessment evaluates clear explanation of thought process, ability to justify design decisions with technical and business reasoning, responding well to feedback and suggestions, articulating trade-offs between different approaches, asking clarifying questions that demonstrate deep thinking, and explaining solutions in a way both technical and non-technical stakeholders would understand.

## Design patterns, SOLID principles, and Python implementation

Mastering the technical approaches for Amazon LLD interviews requires deep understanding of design patterns, SOLID principles, and language-specific implementation considerations, particularly for Python which offers unique features like the ABC module, decorators, and dynamic typing.

### Essential design patterns for Amazon interviews

**Strategy Pattern** is the most frequently tested pattern at Amazon, appearing in approximately 60% of LLD questions. It encapsulates algorithms as interchangeable objects, allowing runtime selection of behavior. Amazon use cases include parking lot systems with different parking strategies (nearest spot, cheapest rate, EV-only sections), file search systems with search by size, extension, or name, e-commerce product sorting by price, rating, or popularity, and customer support systems with different ticket assignment strategies based on expertise, availability, workload, or performance metrics.

The Python implementation using abstract base classes creates clean, testable code. The abstract ParkingStrategy base class defines the interface with an abstract find_spot method accepting parking_lot and vehicle parameters. Concrete strategies like NearestSpotStrategy and CheapestSpotStrategy implement specific algorithms. The ParkingLot class holds a reference to a ParkingStrategy object and delegates spot finding to the current strategy, allowing runtime strategy swapping without modifying ParkingLot code. This demonstrates the Open/Closed Principle perfectly—new strategies can be added by creating new classes implementing ParkingStrategy without modifying existing code.

**Observer Pattern** implements one-to-many dependencies where multiple observers react to subject state changes. Amazon applications include food ordering systems where restaurant rankings update automatically when ratings change, movie booking systems where search displays refresh when new shows are added, and stock brokerage platforms where open orders close automatically when stock prices change. The pattern creates loose coupling—observers don't need to know about each other, and subjects don't need to know observer implementations.

Python implementation creates a Subject class maintaining a list of observers with attach and notify methods. The abstract Observer base class defines an update method accepting the subject. Concrete observers like RestaurantRankingObserver implement update to react to changes. When the subject's state changes, calling notify triggers all observers' update methods. This pattern elegantly solves the "one change, many reactions" problem without tight coupling.

**Factory Pattern** decouples object creation from usage, particularly valuable when object construction is complex or when the specific class to instantiate isn't known until runtime. Amazon scenarios include chess games creating different pieces (King, Queen, Knight with different movement rules), document editors creating different document types with specific formatting, notification systems creating Email, SMS, WhatsApp, or Push notifications, and vehicle systems creating Cars, Trucks, Motorcycles with different characteristics.

The Python factory implementation defines an abstract ChessPiece base class with an abstract move method. ChessPieceFactory provides a static create_piece method accepting piece_type and color parameters, returning the appropriate concrete piece instance. This centralizes creation logic, makes adding new piece types straightforward without modifying client code, and handles creation complexity including validation and default values.

**Singleton Pattern** ensures only one instance exists with global access, but it's the most overused and abused pattern. Use Singleton ONLY when exactly one instance is genuinely required AND accessed from multiple places. Common misuse includes making configuration classes Singletons when dependency injection would be better, creating database connection Singletons that complicate testing, and using Singleton for convenience rather than true requirement. The pattern makes unit testing harder because Singleton state persists across tests, violates dependency injection principles making code less flexible, and creates hidden dependencies that aren't visible in constructors.

When Singleton is genuinely needed—such as for ParkingLot (only one lot in the system) or CentralPaymentSystem (coordinate payment across all exit panels)—Python implementation uses the `__new__` method to control instantiation, checking if `_instance` already exists and returning the existing instance rather than creating new ones. However, before implementing Singleton, consider whether dependency injection would provide better testability and flexibility.

**State Pattern** is ideal when object behavior changes based on internal state, particularly for state machines. Amazon uses include elevator systems with Moving Up, Moving Down, and Idle states handling requests differently, order management with Pending, Confirmed, Shipped, Delivered states, and ATM systems with different states for card validation, transaction, and completion. Each state is represented by a separate class implementing a common interface, with the context object delegating to the current state. State transitions become explicit and manageable rather than buried in nested conditionals.

### SOLID principles in practice

**Single Responsibility Principle** states that each class should have only one reason to change. In a bakery system, separating BreadBaker (handles baking), InventoryManager (manages stock), and CustomerService (handles customer interactions) gives each class a single, clear purpose. The anti-pattern is a monolithic Baker class handling baking, inventory, customer service, and cleaning—any change to any aspect requires modifying this god class, increasing bug risk and making the code difficult to understand and maintain.

**Open/Closed Principle** requires classes to be open for extension but closed for modification. A PaymentProcessor abstract base class defines the interface, with CreditCardPayment, PayPalPayment, and CryptoPayment extending it. Adding new payment methods requires creating new classes, not modifying existing ones. This reduces regression risk—existing payment methods continue working unchanged when new ones are added.

**Liskov Substitution Principle** requires derived classes to be substitutable for base classes without breaking functionality. A classic violation is the Square-Rectangle problem: if Square inherits from Rectangle but overrides set_width to also set height (maintaining the square constraint), code expecting Rectangle behavior breaks. Calling set_width on a Rectangle should only change width, but if a Square is passed, height also changes unexpectedly. The solution is using composition rather than inheritance, or separate hierarchies when the "is-a" relationship doesn't hold for all behaviors.

**Interface Segregation Principle** advocates for specific interfaces over monolithic ones. Instead of one IRestaurantMenu interface with get_vegetarian_items, get_non_vegetarian_items, and get_drink_items, create separate IVegetarianMenu, INonVegetarianMenu, and IDrinkMenu interfaces. A VegetarianRestaurant implements only IVegetarianMenu and IDrinkMenu, avoiding methods it doesn't need. This prevents interface pollution where classes are forced to implement methods they don't use.

**Dependency Inversion Principle** requires high-level modules to depend on abstractions, not concrete implementations. A DevelopmentTeam class depending on IVersionControl abstraction rather than GitVersionControl concrete class allows swapping version control systems without modifying DevelopmentTeam code. The high-level policy (development workflow) doesn't depend on low-level details (specific version control implementation).

### Python-specific implementation techniques

Python's **ABC module with @abstractmethod** provides powerful abstraction capabilities. Importing ABC as base class and abstractmethod decorator creates abstract classes that cannot be instantiated directly and enforce method implementation in subclasses. A Shape abstract base class with abstract area and perimeter methods ensures all concrete shapes implement these methods. Abstract classes can include concrete methods like describe that use abstract methods, demonstrating the Template Method pattern. Attempting to instantiate Shape directly raises TypeError, and subclasses omitting abstract method implementations cannot be instantiated.

The **inheritance versus composition** debate strongly favors composition. Inheritance represents "is-a" relationships where Dog is-an Animal, making inheritance appropriate for inheriting common animal behaviors. Composition represents "has-a" relationships where Car has-an Engine—the car is not a type of engine, so composition is correct. Python best practices favor composition because it's more flexible allowing runtime behavior changes, easier to test with dependency injection, avoids deep inheritance hierarchies that become brittle, and reduces coupling between classes. The adage "favor composition over inheritance" applies strongly in LLD interviews.

**Properties and decorators** provide clean interfaces for attribute access. Using @property decorator creates read-only or computed properties without exposing internal representation. A User class with @property for username makes it read-only, while @property and @reputation.setter for reputation allows validation preventing negative values. This encapsulation protects invariants while maintaining clean syntax.

**Type hints** dramatically improve code clarity and catch errors. Python 3.5+ type hints specify function parameters and return types, making interfaces self-documenting. A User class with type-hinted __init__ method and ask_question method clearly indicates expected types and return values. Type hints also enable IDE autocomplete and static type checking with mypy, catching type errors before runtime.

**Dataclasses** introduced in Python 3.7 reduce boilerplate for simple data containers. The @dataclass decorator automatically generates __init__, __repr__, __eq__, and other special methods. A Comment dataclass with content, author, and created_at fields gets full initialization and comparison functionality without manual implementation. This demonstrates Python's philosophy of reducing boilerplate while maintaining clarity.

### Common pitfalls and best practices

Critical mistakes to avoid include jumping into coding immediately without clarifying requirements (spend the first five minutes asking questions to understand scope), not following SOLID principles by creating god classes with multiple responsibilities (separate concerns into focused classes), overusing design patterns by forcing them where not needed (use patterns naturally when they solve actual problems), ignoring testability by creating tight coupling that's hard to test (use dependency injection and interfaces), using poor naming like generic Manager or Handler classes (use descriptive names like ParkingSpotFinder or UserReputationCalculator), not handling edge cases by assuming only happy paths (discuss error handling, validation, and edge cases explicitly), overusing Singleton when dependency injection would be better (reserve Singleton for genuine single-instance requirements), creating deep inheritance hierarchies more than two to three levels deep (favor composition for flexibility), not communicating by coding silently (explain your thought process continuously), and ignoring concurrency when required (discuss synchronization, atomic operations, and thread-safe collections when problems involve concurrent access).

Best practices for code structure follow a systematic approach. First, clarify requirements by asking about core features, users and their actions, scale and performance requirements, concurrency needs, and edge cases. Second, identify entities by listing main nouns in the problem—for Stack Overflow these include User, Question, Answer, Comment, Tag, and Vote. Third, define classes and relationships with clear attributes and associations. Fourth, define interfaces and methods with abstract base classes for common behaviors. Fifth, create a central coordinator class managing interactions between components. Sixth, implement key methods focusing on what interviewers want to see with clean, readable code and comments for complex logic. Seventh, address concurrency if required using threading locks for critical sections. Eighth, implement exception handling for validation and error conditions.

## Success strategies and final recommendations

Amazon LLD interviews reward preparation, clear thinking, strong fundamentals, and excellent communication. Candidates who master core concepts and practice systematically significantly outperform those relying on native intelligence alone.

During the interview, follow these critical strategies. Always ask clarifying questions first before writing any code, spending five minutes understanding requirements thoroughly by asking about functional requirements (what should the system do), non-functional requirements (performance, scalability, constraints), edge cases and error conditions, and expected scope (which features are in scope versus nice-to-have). Start with high-level design by identifying main classes and their responsibilities, defining relationships between classes, discussing which design patterns apply and why, and getting interviewer buy-in before detailed implementation.

Explain your thought process continuously, verbalizing your reasoning as you work. State why you're choosing specific approaches, mention trade-offs you're considering even when choosing one option, ask for feedback on your direction, and narrate what you're implementing as you code. Use SOLID principles explicitly, mentioning them by name when your design demonstrates them. Explain "This follows Single Responsibility Principle because..." or "I'm using an interface here to follow Dependency Inversion Principle..." demonstrating that you're not just accidentally writing good code but intentionally applying principles.

Consider extensibility throughout by designing for change, explaining "If we need to add X feature later, we would create a new class implementing this interface..." Show you're thinking beyond immediate requirements by discussing how to handle future vehicle types, new payment methods, and different parking strategies. Avoid hard-coding values that should be configurable like number of floors, spots per floor, or pricing rates.

Discuss trade-offs explicitly comparing alternatives: "Using a HashMap gives us O(1) lookups but uses more memory than an array. Given that lookup speed is critical for ticket validation at exit points with high throughput, the memory trade-off is acceptable." This shows mature engineering judgment understanding that no design is perfect and making explicit choices based on priorities.

Handle edge cases proactively by discussing validation before interviewers ask, mentioning error conditions like "What happens when the lot is full?" or "How do we handle invalid payment?" even if not implementing complete error handling, and showing you're thinking about production concerns beyond happy paths.

Keep designs appropriately simple, avoiding over-engineering with unnecessary patterns. Use design patterns when they solve actual problems in your design, not just to demonstrate pattern knowledge. The simplest solution that meets requirements is often best, showing restraint and judgment.

Write clean code following these practices: use meaningful names for classes, methods, and variables that are self-documenting; apply proper formatting with consistent indentation; structure code logically with public methods at top, private helpers at bottom; add type hints throughout for clarity; and include comments explaining complex algorithms or non-obvious design decisions.

Leave time for testing discussion by explaining how you would test your solution with unit tests for individual classes, integration tests for component interactions, and edge case tests for boundary conditions. Discuss testing strategies even when not writing actual test code, showing you think about code quality beyond initial implementation.

What interviewers look for includes problem understanding and requirement clarification skills, object-oriented thinking with natural application of OOP concepts, SOLID principles application demonstrating mature design skills, appropriate design pattern usage without forcing patterns unnecessarily, clean readable code that would be maintainable in production, extensibility and maintainability in your design, edge case awareness and error handling, communication skills in explaining decisions, trade-off analysis showing engineering judgment, and testing mindset thinking about verification.

Red flags to avoid include jumping to code without understanding requirements, creating god classes with multiple responsibilities, tight coupling between classes making changes difficult, ignoring SOLID principles or applying them incorrectly, not handling edge cases or error conditions, poor naming conventions like x, temp, or data, silent coding without explanation, over-engineering with unnecessary complexity, not considering extensibility making future changes difficult, and ignoring concurrency when the problem clearly involves it.
